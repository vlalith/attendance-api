# REVIEW.md

Defects found in the starter `app/main.py`:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `health()` (line 73–74) | MongoDB is never actually pinged — the health endpoint always returns 200 even when the database is down. | Start the app without MongoDB running; `GET /health` still returns `{"status": "ok"}`. | Run `client.admin.command("ping")` inside a try/except and return 503 on failure. |
| 2 | `create_employee()` — check-then-insert race (lines 79–85) | The existence check with `find_one` followed by `insert_one` is not atomic. Two concurrent requests for the same `emp_code` can both pass the check and both insert, violating the uniqueness requirement. | Hammer the endpoint with concurrent duplicate requests; you'll get two 201s and two documents. | Remove the manual `find_one` check; rely solely on the unique MongoDB index on `emp_code` and catch `DuplicateKeyError`. |
| 3 | `create_employee()` — `created_at` is naive (line 82) | `datetime.now()` returns a naive local-time datetime. If the server is not in UTC, the stored timestamp is wrong. PyMongo will store it as-is and it will be interpreted as UTC on retrieval. | Run the server in a non-UTC system timezone; the returned `created_at` will differ from reality. | Use `datetime.now(timezone.utc)` for an explicit UTC-aware datetime. |
| 4 | `create_employee()` — `created_at` returned as a `datetime` object (lines 84–85) | The raw `doc` is returned after popping `_id`. `created_at` is still a `datetime`, so FastAPI serialises it as an ISO string. The spec requires epoch **milliseconds** (integer). | Call `POST /employees`; `created_at` in the response will be a string like `"2026-07-06T09:40:00"` instead of an integer. | Serialise with `dt_to_ms()` before returning. |
| 5 | `list_employees()` — wrong `skip` calculation (line 93) | `skip = page * page_size` skips one extra page. Page 1 should skip 0, but the code skips `page_size` documents. | `GET /employees?page=1` returns the second page of employees instead of the first. | Change to `skip = (page - 1) * page_size`. |
| 6 | `list_employees()` — `total` ignores the `department` filter (line 94) | `count_documents({})` counts the whole collection, not the filtered subset. The spec says "`total` counts the filtered set". | Filter by department; `total` will be the count of all employees, not just that department. | Pass the same query `q` to `count_documents(q)`. |
| 7 | `list_employees()` — `created_at` not serialised to epoch ms | Same as defect 4: `created_at` is returned as a `datetime` object in list results. | `GET /employees`; every employee's `created_at` is a datetime string, not an integer. | Serialise each item with `serialize_employee()`. |
| 8 | `punch_in()` — `datetime.fromtimestamp()` uses local time (line 102) | `fromtimestamp` converts using the local system timezone. On a non-UTC server the stored datetime is wrong. | Run server in IST; a `punched_at` epoch ms will produce a BSON datetime 5.5 h off from UTC. | Use `datetime.fromtimestamp(ms/1000, tz=timezone.utc)` (or the helper `ms_to_dt`). |
| 9 | `punch_in()` — attendance `date` ignores overnight shifts (line 103) | `ts.date().isoformat()` uses UTC date, not IST. Also, for overnight shifts a punch-in before `shift_end` must belong to the previous day. | EMP0005 has a 22:00–06:00 shift. A punch-in at 05:55 IST (00:25 UTC next day) would get the wrong date. | Compute IST date and apply overnight-shift rule (R1) via `attendance_date()`. |
| 10 | `punch_in()` — returns `id` field (MongoDB ObjectId) instead of compliant shape (line 119) | The spec says `_id` is internal and must never appear in a response. The code adds `"id"` (stringified ObjectId) to the response. | `POST /attendance/punch-in`; response has an extra `"id"` field not in the schema. | Remove the `doc["id"] = ...` line; use `serialize_record()` to produce the correct shape. |
| 11 | `punch_in()` — missing 404 check for unknown employee | If `emp` is `None` (employee not found), the next line `emp["shift_start"]` raises an unhandled `TypeError`/`KeyError`, producing a 500. | Send a punch-in for a non-existent `emp_code`; get a 500 instead of 404. | Add `if not emp: raise HTTPException(404, ...)` after the `find_one`. |
| 12 | `compute_late_minutes()` — uses a naive `replace()` which breaks for datetimes with a timezone (line 35) | `punch_in.replace(hour=h, minute=m, ...)` builds a naive datetime regardless of the input's timezone, so the subtraction mixes aware and naive objects and raises a `TypeError`. | Pass an aware (timezone-attached) datetime; the call crashes. | Work entirely in IST-aware datetimes or strip timezone consistently before arithmetic. |
| 13 | `compute_late_minutes()` — wrong late check: `minutes > 10` should use floor (line 37) | The grace period is strictly more than 10 minutes. The code divides by 60 with `/`, giving a float, then compares as `> 10`. Integer floor division should be used (R2). | Punch in at 09:40:30 with shift 09:30; diff is 10.5 min, `int(630/60)=10`, so `10 > 10` is False → 0 late minutes. That is correct by coincidence for this case. But `int()` truncates, not floors — for negative diffs (early punch) it would give wrong results too. | Use `int(diff_seconds // 60)` (floor division) and compare `> 10`. |
| 14 | `compute_overtime()` — ignores overnight shifts (line 46) | `datetime.fromisoformat(date_str).replace(hour=h, minute=m, tzinfo=IST)` always places `shift_end` on the attendance date. For an overnight shift (e.g., 22:00–06:00), `shift_end` is on the *next* calendar day. | EMP0005 (22:00–06:00): `shift_end` is placed at 06:00 on July 6 instead of July 7. Punch-out at 06:40 July 7 is subtracted from 06:00 July 6, giving 24 h 40 min of "overtime". | Detect overnight shift and add one day to `end_date` before building `shift_end_dt`. |
| 15 | `list_attendance()` — loads entire collection into memory (lines 144–146) | `list(db.attendance_logs.find(q))` fetches all matching documents, then sorts and paginates in Python. At 100k records this will be slow and memory-hungry. | Run against a large collection; response time degrades linearly. | Use MongoDB `.sort().skip().limit()` and `count_documents()` rather than loading all docs. |
| 16 | `department_trend()` — `$densify` expression bounds crash in MongoDB | `$densify` `bounds` was passed expression objects `{"$dateFromString": ...}` rather than literal date objects, causing MongoDB `OperationFailure: A bounding array must be an ascending array of either two dates or two numbers`. | Calling `GET /analytics/departments/{dept}/trend` crashes with code 5733402. | Construct BSON UTC `datetime.datetime` objects in Python and pass them directly into the `$densify` bounds array. |
| 17 | `explain_endpoint()` — `explain=True` on PyMongo 4 `aggregate()` & Binary UUID decoding | PyMongo 4.x removed `explain=True` from `collection.aggregate()` (raises `ConfigurationError`), and unhandled BSON `Binary` UUIDs in explain output cause `UnicodeDecodeError` in FastAPI's `jsonable_encoder`. | Calling `GET /admin/explain/employee_monthly` fails with `ConfigurationError` or `UnicodeDecodeError`. | Use `db.command("aggregate", ..., explain=True)` and sanitize the document via `json.loads(json_util.dumps(doc))`. |

### Items reviewed and decided NOT a defect

- **`compute_work_hours` uses `round()`** — Python's built-in `round()` uses banker's rounding. This was not yet called from any complete flow in the starter, but would produce incorrect results. It was noted and fixed by using `half_up_round()` (R4).
- **`IST = timezone(timedelta(hours=5, minutes=30))`** — correctly defined; not a defect.
